# MG Intelligence Hub v3 — 可行性审查报告

> 审查日期：2026-06-16
> 审查对象：`项目规划-v3-clean.md`（v3.0，设计定稿）
> 审查范围：项目目的、现有资产、规划可行性、风险与优化建议
> 审查方法：逐文件阅读实际代码 + 数据实测 + 与规划文档逐条交叉比对

> - 推进范围：**全部 7 阶段**
> - 数据校准：**全部用实测数字重写附录**

## 一、总体结论

**规划的愿景（从"数据展示台"升级为"医学事务 AI 变革引擎"）方向正确、理念清晰，四大工作流与 MSL 闭环设计有真实业务价值。但规划文档对现有系统的认知存在系统性偏差，导致工作量估算过于乐观，且存在若干会导致实施即失败的硬性缺陷。建议在进入编码前先做规划校准（已产出 v3.1 修订版）。**

### 三句话定性

1. **理念 ★★★★★**：信号驱动、工作流优先、LLM 做提取不做生成 — 这三条原则经得起推敲，是整个规划的最大资产。
2. **现状认知 ★★☆☆☆**：附录的数据盘点与实际代码/数据差数倍，多处页面/文件位置描述错误，"70% 可复用"的判断建立在错误前提上。
3. **可执行性 ★★★☆☆**：阶段 1-2 可立即落地且价值明确；阶段 3-4 有数据合规与使用频率的现实约束；阶段 7 的"自动化流水线"缺少对运行环境的定义。

## 二、项目目的审查

### 2.1 项目定位（原样认可）

> MA-MG-HUB：围绕 MSL/MA 工作流的主动赋能系统，情报驱动型。

**审查意见：认可。** 这个定位把"我有什么数据"翻转成"用户要做什么"，是正确的产品思维转向。四大工作流（情报感知 → 知识管理 → 学术产出 → MSL 闭环）覆盖了医学事务的核心价值链，且每个工作流都有明确的"当前痛点 → 目标态"对照。

### 2.2 MSL 闭环的设计价值（核心亮点）

**阶段 3 的"记忆感知循环模式"是整个规划最值得保留的设计。** 它的正确之处在于：

- 区分"新拜访"与"回访"，起点不同（画像+热点 vs 纪要+follow-up）— 这抓住了 MSL 工作的真实节奏
- Follow-up 清单由系统自动维护而非 MSL 手动记录 — 这是真正的"减负"，不是给 MSL 增加录入负担
- 拜访产出成为下次输入 — 形成飞轮，这是"情报系统"区别于"录入系统"的关键

**但有一个被低估的约束：** 这个闭环的价值完全依赖**团队持续录入拜访数据**。若 MSL 录入率低，回访简报就退化为"画像+热点"（即新拜访模式），飞轮不转。规划没有讨论"如何保证录入率"，这是阶段 3 成败的关键非技术因素。

### 2.3 ROI 表（§7）审查

规划 §7 的 ROI 表是说服性的，但有一项需修正：

| 规划声称 | 审查意见 |
|:--|:--|
| "MSL 每次拜访效率提升 30 min+" | ⚠️ 这是**生成简报**的效率，但**录入拜访记录**会增加 5-10 min。净收益取决于简报生成质量与录入工具的易用性。建议改为"拜访前准备节省 30 min，拜访后录入增加 5-10 min，净节省 20-25 min"。 |

## 四、逐阶段可行性评估

> 工作量估算基于"静态站 + 轻量后端"形态，以"会话"为单位（1 会话 ≈ 1 个专注工作单元，约 2-4 小时实际编码）。

### 阶段 1：情报中心重构

| 维度 | 评估 |
|:--|:--|
| 可行性 | ★★★★★ 高 |
| 前置依赖 | LLM 引擎层（OpenRouter/DeepSeek 调用封装）必须先建 |
| 数据就绪 | ✅ 近1年 1,154 篇，证据等级 72%，完全够用 |
| 主要工作 | ① LLM 客户端封装 ② `extract-signals.py` ③ `build-china-intelligence.py` ④ literature.html 加 2 个标签页 |
| 风险 | LLM 成本与稳定性（规划估 $0.5/周合理）；信号质量需 prompt 调优 |
| 规划估算 2 会话 | ⚠️ 偏乐观。LLM 封装 + 两个脚本 + 前端两标签 + prompt 迭代，实际 3-4 会话 |

**审查建议：** 阶段 1 拆出一个"阶段 0"——先建立 LLM 引擎层基础设施（客户端、配置、调用规范、成本日志），所有后续阶段复用。否则每个脚本各自处理 API 调用会重复且难维护。

### 阶段 2：MSL 专家画像

| 维度 | 评估 |
|:--|:--|
| 可行性 | ★★★★★ 高 |
| 前置依赖 | 阶段 1 的 LLM 层（非必须，词频统计版可纯本地） |
| 数据就绪 | ✅ 39,334 作者，556 人发文≥10 篇，数据极充分 |
| 主要工作 | ① `experts-core.json` 模板 ② `build-expert-profiles.py`（词频+共发统计） ③ 前端画像卡片 |
| 风险 | 姓名消歧（同名 + 中文拼音转英文）。规划方案 C（核心专家名单+机构消歧）合理 |
| 规划估算 2 会话 | ✅ 合理 |

**审查建议：** 专家画像的"研究兴趣向量"先用纯词频（TF），验证 MSL 觉得有用后再上 TF-IDF/LLM 主题提取。避免过度工程。

### 阶段 3：MSL 拜访闭环

| 维度 | 评估 |
|:--|:--|
| 可行性 | ★★★☆☆ 中（技术可行，但依赖使用频率与数据合规） |
| 前置依赖 | 阶段 1+2；**轻量后端**（拜访记录需写入存储，纯静态站无法实现） |
| 数据就绪 | ❌ 无任何拜访历史数据，需从零积累 |
| 主要工作 | ① 拜访记录数据结构 ② 前端录入表单（结构化） ③ 回访简报生成 ④ Follow-up 追踪系统 ⑤ 团队信号汇总 |
| 关键风险 | **录入率**：若 MSL 不持续录入，飞轮不转，回访简报退化为新拜访模式 |
| 合规风险 | 🟡 专家姓名、机构、拜访内容属于个人信息/商业敏感数据，存储位置需评估（本地/后端/加密） |

**审查建议：**
1. 阶段 3 应先做一个"最小闭环 MVP"：单 MSL、3-5 位核心专家、只做新拜访简报 + 结构化录入 + follow-up 列表。验证录入意愿和简报质量后，再扩展到团队汇总和回访衍生信号。
2. 数据存储：拜访记录建议初期存本地 JSON（gitignore），或后端用 Cloudflare KV/D1（免费额度够用）。**不要把专家拜访数据提交到公开 GitHub 仓库。**

| 无统一客户端 | 规划有 6+ 个脚本要调 LLM，若无封装会重复造轮子 | 建阶段 0：`scripts/llm_client.py` 统一封装（模型、重试、成本日志、本地缓存） |
| 模型选择 | 规划 §9.6 写"DeepSeek v4 flash"，但 DeepSeek 无 "v4 flash" 型号 | 改为：DeepSeek-V3（主） + 本地缓存；或 OpenRouter 路由 |
| 成本失控 | 14 步管线若每步都调 LLM，成本会超 $0.5/周 | 区分"高频低质"（用便宜模型）与"低频高质"（用好模型） |
| 本地缓存 | 相同输入不应重复调用 | LLM 调用按 prompt hash 缓存到本地 |

### 5.2 数据合规（阶段 3-4 的隐性约束）

| 数据 | 性质 | 存储建议 |
|:--|:--|:--|
| 专家姓名/机构/发文 | 公开（PubMed） | 可入公开仓库 |
| 专家 priority/msl_owner/tags | 内部分类 | gitignore，不入公开仓库 |
| 拜访记录（讨论内容、专家观点） | 🔴 商业敏感 + 个人信息 | 本地或加密后端，**绝不入 GitHub** |
| 团队信号汇总（共性趋势） | 聚合后脱敏 | 可入仓库 |

**现状 `.gitignore` 只忽略了 `literature-full.json`/`archive/`/`literature-recent.json`**，未规划拜访数据的隔离。v3.1 必须补充。

### 5.3 前端架构（纯 JS vs 框架）

现状是纯原生 JS（literature.js 450 行手写筛选/分页/简报篮）。阶段 3-4 的录入表单、模块组装界面、多标签页交互，若继续用纯 JS 会非常冗长。

**审查建议：** 不必引入 React/Vue（增加构建链复杂度，与 GitHub Pages 静态部署有摩擦）。但建议引入 **Alpine.js 或 htmx**（单文件 CDN，零构建，能大幅简化交互状态管理）。这是轻量后端形态下的合理折中。

### 5.4 测试与质量保障

现状无任何测试。LLM 提取脚本（信号、证据矩阵、模块）的输出质量**必须**有验证机制，否则错误信号会误导 MSL。

**审查建议：** 每个 LLM 脚本配套一个 `golden-set`（10-20 条人工标注的输入→期望输出），管线跑完后对比。不追求自动化测试框架，但要有人工抽检的锚点。
